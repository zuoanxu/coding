# 压测说明（order-stock-demo）

## 一、压测前准备（缺一不可）

```bash
# 1. 启动依赖：MySQL + Redis + RocketMQ（namesrv/broker/dashboard）
docker compose up -d
# 确认三个容器 Up：docker ps

# 2. 启动应用（另一个终端）
mvn spring-boot:run
# 或 IDEA 里运行 OrderApplication
```

> ⚠️ **下单接口依赖 RocketMQ**。`OrderService.createOrder` 最后一步会
> `rocketMQTemplate.syncSend("order-delay-topic:cancel", msg, 5000, 16)` 同步发延时消息，
> 若连不上 broker，每个下单请求会等 5 秒超时后回滚返回 500。
>
> ⚠️ **broker.conf 里 `brokerIP1 = 192.168.43.11` 是写死的局域网 IP**，
> 必须改成你本机实际 IP（`ipconfig` 查）或 `127.0.0.1`，否则应用里的 producer 拿到这个地址连不上 broker，下单必失败。

## 二、导入并运行 JMeter 脚本

1. 打开 JMeter（GUI 模式），`文件 → 打开` 选择 `order-stock-load-test.jmx`。
2. 左侧树里有 **两个线程组**：
   - **① 读接口压测**：商品列表 / 商品详情 / 概览统计 / 订单列表（只读）
   - **② 下单接口压测**：创建订单（核心写链路）
3. 点绿色 ▶ 按钮运行，在「聚合报告 / 汇总报告」里看结果。

## 三、关键参数在哪改

| 想改什么 | 在哪改 |
| --- | --- |
| 目标机器 | 测试计划下「全局变量」里的 HOST / PORT |
| 并发数（虚拟用户） | 线程组的 `线程数` |
| 启动快慢 | 线程组的 `Ramp-Up 时间（秒）` |
| 每个线程跑多少轮 | 线程组的 `循环次数` |
| 下单的商品范围 | 创建订单请求体里 `${__Random(1,6)}`（商品 6「机械键盘」只有 8 库存，故意用来演示库存不足） |

## 四、怎么看结果（聚合报告关键列）

| 列 | 含义 |
| --- | --- |
| # Samples | 请求总数 |
| Average / Median | 平均 / 中位数响应时间 |
| 90% / 95% / 99% pct | 90/95/99 分位响应时间（看长尾，比平均值重要） |
| Error % | 失败率，**>0 就要警惕** |
| Throughput | 吞吐量 TPS（每秒处理请求数），**衡量系统能力的核心指标** |

## 五、建议的压测步骤（从低到高）

1. **冒烟测试**：1 线程 × 1 循环，跑通，看有没有 500（尤其是下单，验证 RocketMQ 通了）。
2. **基线**：10 线程，记下 TPS 和响应时间。
3. **加码**：50 → 100 → 200 → 500 线程，每次记录 TPS 和 Error%。
4. **找拐点**：当「线程数继续加、但 TPS 不再涨、响应时间明显上升或 Error% 开始出现」时，就是系统瓶颈，当前线程数附近即最大承载。

## 六、本项目常见的失败原因

- 下单 `Error%` 接近 100% → RocketMQ 没起来，或 broker.conf 的 IP 不对。
- 下单报「库存不足」→ 商品 6 只有 8 库存，属正常业务拒绝（这是乐观锁防超卖的效果）；把 productId 范围改成 1-5 即可全成功。
- 业务失败但 HTTP 状态码是 200 → 本项目 `GlobalExceptionHandler` 返回 `{"code":400/500}` 但 HTTP 码仍是 200，所以断言检查的是 body 里的 `"code":200`，不是响应码。

## 七、命令行非 GUI 压测（更准，适合高并发）

GUI 模式本身吃资源、结果会失真。真正压大并发建议命令行：

```bash
jmeter -n -t order-stock-load-test.jmx -l result.jtl -e -o report
# -n 非 GUI  -t 脚本  -l 结果文件  -e -o 生成 HTML 报告
```

压完用浏览器打开 `report/index.html` 看漂亮的图表报告。
